## 一、结论先行（TL;DR）

1. **方向成立，且比方案作者预估的更可行**：方案第一验证对象「猫」在项目里**已有 60% 基础**——青禾镇已有 2 只程序绘制的猫（靠近自动摆尾），已有程序合成猫叫音效，已有集中式交互框架。V0.1 最小闭环实际是"补全现有猫的交互"，不是从零做。
2. **2026-08-12 Alpha Freeze 已解除、进入第一章开发阶段（D-027）**，猫互动作为第一章 P2 轻量玩法候选进入评估通道。但**是否放行仍由制作人拍板**——按第一章总纲：玩法必须服务生活感、不引入复杂数值；判断标准="玩家是否因此更喜欢这个小镇"。
3. **对方案的两处修正**：① 方案说"复用 Interaction 系统"，项目实际**没有独立 Interaction 文件**，交互集中在 `MapScene.tryInteract()`；② 捕虫（蝴蝶）优先级应**下调**——现有蝴蝶是纯装饰，做捕捉需要新系统，成本远高于猫，建议进未来池。
4. **猫 V0.1 改动极窄**：给 2 只已存在的猫补"点击/E 键 → 喵叫 + 摆尾 + 文字气泡"，改动收敛在 MapScene 一个文件内，零新素材、零新音效文件（meowSound 已存在）。
5. **本批次交付**：现状盘点表 + 分阶段计划（P0~P4）+ 每阶段验收标准与失败信号 + 复用清单。**未改任何代码。**

### 2.2 方案核心假设 vs 项目现实

| 方案假设 | 项目现实 | 影响 |
|---|---|---|
| "复用 Interaction 系统" | 无独立 Interaction 模块，交互集中在 `MapScene.tryInteract()` 方法链 | 落地时改 MapScene 方法链，不新建系统 |
| "一只猫需要一个角色素材" | 猫已是 Graphics 程序绘制，**零素材成本** | P0 资源验证其实已通过，只需确认风格是否达标 |

### 2.3 关键结论

> **猫互动 V0.1 的隐藏成本远低于方案预估**：对象、位置、音效、交互框架全部已有，缺的只是"把交互挂上"。真正的成本集中在两处——① meowSound 导出与绑定；② 交互反馈的**质感**（猫转头/眯眼等反馈动画 vs 现在只有摆尾）。

## 三、合规性判定（2026-08-12 解冻后的评估框架）

> 背景：Alpha Freeze 已解除（D-027），进入第一章「复苏」阶段。猫互动改按**第一章总纲 P2 轻量玩法**评估：必须服务生活感、不引入复杂数值系统、不触碰第0章已冻结内容；立项仍需制作人拍板。

### 3.1 第一章禁止项对照

| 第一章禁止条款 | 猫 V0.1 是否触碰 | 判定 |
|---|---|---|
| 禁止无限扩张（大地图/新大陆/大量 NPC/复杂剧情线） | 否——复用现有 2 只猫，零新增对象 | ✅ 不触碰 |
| 禁止偏离核心玩法（战斗/装备/抽卡/复杂制造链） | 否——生活感互动，无数值系统 | ✅ 不触碰 |
| 禁止为"看起来丰富"增加内容 | 边界项——"点击猫获得反馈"是新玩法但极轻 | ⚠️ 需制作人判断（是否增强"人与小镇连接"） |
| 禁止第0章内容回归/变动（D-021/023/025） | 否——纯新增轻互动，不动已冻结体验 | ✅ 不触碰 |

### 3.2 服务生活感评估（第一章总纲 §五 P2）

> 若改动显著增强"人与小镇的连接"，且同时满足：①修改范围可控 ②不引入新系统 ③有自动化验证 → 可进评估，最终由制作人拍板。

| 条件 | 猫 V0.1 | 结论 |
|---|---|---|
| 显著增强"人与小镇的连接" | "世界有东西可以碰"正是总纲要验证的核心；展示时猫互动是 30 秒内可见的治愈点 | ✅ 满足（制作人判断权重最高） |
| 修改范围可控 | 收敛在 `MapScene.ts`（猫交互分支）+ `AmbienceSystem.ts`（导出 meowSound），约 30~60 行 | ✅ 满足 |
| 不引入新系统 | 不新建 Manager / 不建 InteractableObject 抽象（第一只猫不抽象，符合方案"不要提前过度工程化"） | ✅ 满足 |
| 有自动化验证 | 新增/扩展探针：模拟靠近+触发交互，断言反馈动画/音效被调（现有 probe-town-life 可扩展） | ✅ 满足 |

### 3.3 判定建议

- **推荐路径 A（放行做 P1）**：猫互动按"现有功能表现增强 / 第一章 P2 轻量玩法"走评估通道，改动极窄且是方案明确的第一验证对象，风险低、展示收益高。
- **备选路径 B（仅归档）**：方案进 `docs/design/` 归档为未来玩法池，等制作人排期后再做。本计划文档已保证两种路径都可执行。
- **捕虫**：本次**明确不做**，进未来池（见 §六）。

## 四、落地计划（P0 → P4）

> 遵循方案"十一、当前实际开发顺序"，但按现状压缩。每阶段含：改动范围 / 复用项 / 新增项 / 验收标准 / **失败信号**（先定义"坏掉长什么样"再动手）。

### P0 — 资源验证（视觉风格达标确认）

- **现状**：猫已是 Graphics 程序绘制（棕色几何猫）。方案的 P0 目标是"能否做出符合归星物语美术风格的可互动猫"。
- **动作**：**纯评审，不施工**——制作人/美术确认现有 Graphics 猫是否"看起来像同一个游戏"。
- **验收标准**：现有猫风格达标（像素风协调），或给出明确的风格整改清单（如加轮廓线/改配色/换 spritesheet 帧）。
- **失败信号**：猫与场景风格割裂、玩家第一眼认不出是猫 → 回退为"用 tileset 帧/出图管线做一只猫"再进 P1。

### P1 — 最小互动闭环（本方案核心验证）

目标：`一只猫 → 点击/E → 喵叫 + 摆尾 + 文字气泡 → 结束`，且**可重复互动**。

**改动范围**：
1. `AmbienceSystem.ts`：导出 `meowSound()`（约 1 行）。
2. `MapScene.ts`：
   - 猫对象（`cat()` 工厂）挂 `setInteractive`（Graphics 容器），绑定 `pointerdown` + 靠近按 E（并入 `tryInteract()` 方法链）。
   - 互动触发：`meowSound()` + 复用现有摆尾 tween + 短文字气泡（用 `showDialogueText` 或更轻量的浮字）。
   - 状态：互动**冷却可重复**（去掉"一次性"限制，或改为冷却 5~10 秒；不需要持久化——猫互动无存档意义，除非制作人要求"摸过猫"留痕）。
3. 视制作人要求可选：猫反馈动画升级（转头/眯眼/舔爪），保持"不抢戏"低频原则。

**验收标准（对方案五项）**：
- 玩家会主动靠近猫（视觉可发现）
- 点击/E 有即时反馈（喵叫 + 动画 + 文字三通道同时）
- 反馈自然（不是弹窗式打断，是"它真的叫了一声"）
- 玩家愿意再次互动（冷却后可重复）
- 放在青禾镇里自然（不突兀、不挡路）

**失败信号**：
- 玩家路过猫不靠近 / 不点击（发现度失败）
- 点击后无感知（反馈通道失效）
- 猫互动与现有 NPC 对话/剧情对白冲突（注意 StoryDialogue 单实例红线：互动气泡不得覆盖正在播的对白，须走 `isOpen()` 守卫或轻量浮字）

### P2 — 进入真实地图

- **现状**：猫已在 town 地图（左上屋墙角 c1、右下屋墙角 c2）。
- **动作**：仅微调——确认猫不在 NPC 站位/交互点/碰撞区上（现状已避开），必要时加 1 只（如 farm 木屋旁）但**不超 3 只**（低频原则）。
- **验收标准**：任何 NPC 日程时段猫都不与 NPC 重叠；多场景不新增对象数量失控。
- **失败信号**：猫与 NPC 重叠、玩家误触 NPC 对话。

### P3 — 真实玩家测试

- 观察"玩家会不会主动摸猫"。用现有试玩流程（30 分钟体验测量版）顺带观测，不单独立项。
- 评估五问：主动发现 / 主动互动 / 即时反馈 / 自然感 / 再互动意愿。
- **失败信号**：五问中 ≥3 项否定 → 砍掉猫互动，不因写了代码继续堆（方案第十节原话）。

### P4 — 决定是否扩展

- 成立 → 抽象 `InteractableObject`（等第二、第三种互动对象出现时再做，**不在 V0.1 做**）→ 更多动物 → 简单行为。
- 不成立 → 暂停，猫互动仅保留为"镇上的生活装饰"（现状已成立，零额外成本）。
