**不是增加大量系统。**

## P1 第一章核心体验

### P1-1 老屋整理（**优先级最高，玩家第一个动作**）

目标：玩家从"被安排的过客"变为"主动安顿的主人"。**零数值影响**（床/灯/书桌/小物件不改任何属性），每次整理推进"这里是家"的认知。

文件：

- `src/scenes/MapScene.ts`（复用 house 场景交互物范式：`setupMusicBox` / `setupGrandpaGift` / `tryMusicBoxInteract` / `grantGrandpaGift`）
- `src/systems/EventManager.ts`（`triggerOnce` 一次性事件判重）
- `src/systems/ChapterSystem.ts`（`chapter >= 1` 门禁）
- `src/data/MemoryFlashbacks.ts` + `src/ui/MemoryFlashback.ts`（收音机记忆，`playMemoryFlashback` API）
- `src/systems/SaveSystem.ts`（`triggeredEvents` 存档持久化，无需新增存档字段）

内容——四个交互点：

| 交互 | 作用 | 事件 key |
|---|---|---|
| 床 | 重新生活（家感第一步） | `ch1_bed_done` |
| 灯 | 家的感觉（光=有人住） | `ch1_lamp_done` |
| 书桌 | 林澈过去与现在（电脑上桌＝把过去的自己带进来） | `ch1_desk_done` |
| 收音机 | 过去的生活痕迹（旋钮转动 → 爷爷的旧电台记忆） | `ch1_radio_done` |

完成全部四个点 → 聚合事件：

```
ch1_house_tidy_done
```

**完成状态视觉层（硬性要求）：`getHouseTidyLevel()`**

- 不要只依赖 `hasTriggered()` 动态判断单个事件。
- 新增**派生函数** `getHouseTidyLevel(): number`，**不新增存档字段**：

```
getHouseTidyLevel() = count( ch1_bed_done, ch1_lamp_done, ch1_desk_done, ch1_radio_done )
   // 取值 0 / 1 / 2 / 3 / 4
```

- 用途：整理到一半回屋看到不同状态、NPC 评论房间、村长触发条件等都以等级派生。
- 来源：直接对已触发的 `ch1_*_done` 事件计数（`triggeredEvents` 已持久化，读档天然恢复）。

验收：

- 四个交互点逐个可整理，完成后环境视觉变化（灯亮 / 床铺好 / 桌面有电脑 / 小物件整齐）
- **整理 2/4、3/4 时回屋可见中间状态（按 `getHouseTidyLevel()` 派生，非仅 0/4 两态）**
- 收音机触发一段过去的声音（MemoryFlashback，零新素材优先，可程序合成旧电台感）
- **保存退出重新进入：状态保持**（`triggeredEvents` 判重，整理过的点不再出现；全部完成则 `ch1_house_tidy_done` 保持触发，`getHouseTidyLevel() === 4`）
- 玩家整理完全部 4 点后，能说出"这间屋子开始是我的了"

### P1-2 村长来访 / 复兴计划

目标：主线启动。**不是"任务发布"，而是"有人愿意回来，所以大家想试试"**——村长给的是可能性，不是工作清单。

文件：

- `src/systems/StorySystem.ts`（第一章对话数据 + 触发判定）
- `src/data/` 对话数据（DialogueData，遵守 D-017/D-018/D-019 文风护栏）
- `src/systems/NPCSystem.ts`（村长演出/来访）
- `src/systems/EventManager.ts`（`triggerOnceIf`）

条件：

```
chapter >= 1
&&
getHouseTidyLevel() === 4  // 或 ch1_house_tidy_done
&&
夜晚判定（getTime().hour >= 18 || getTime().hour < 6，复用 AmbienceSystem.isNight 逻辑）
&&
!hasTriggered('ch1_mayor_visit')
```

触发窗口（硬性，防"整理完最后一个物品村长突然出现在房间"）：

```
完成整理（getHouseTidyLevel() === 4）
   ↓
离开老屋（回 farm / 换场景）
   ↓
进入下一次夜晚
   ↓
触发村长来访
```

触发形式：夜晚，林澈整理好的屋子里——村长来访（窗外能看到青禾镇的灯光）。

> 工程：无需新系统，仅按上述条件组合判定即可；首次触发后 `triggerOnce('ch1_mayor_visit')` 持久化，读档不重复。

验收：

- 玩家整理完老屋后，下一次合适时机触发村长来访对话
- 不出现"主线任务：青禾复兴计划（进行中）"式任务面板文案
- 对话中玩家有主动选择（呼应观星夜三选项的延续），且选择可入档或留档

### P1-3 夏雅《旧日留影》

**注意：不是完整心语任务，不做「春深有信」全流程。**定位：人物性格铺垫。

目标：引出夏雅"保存小镇记忆"的性格底色——不是等待过去，而是**保存过去，让未来有东西可以连接**。

文件：

- `src/systems/NPCSystem.ts`
- `src/ui/StoryDialogue`（对话演出）
- `src/data/MemoryFlashbacks.ts` + `src/ui/MemoryFlashback.ts`
- `src/systems/EventManager.ts`（复用 `xiya_garden` / `xiya_photo` 一次性支线范式）

触发：整理老屋时翻出旧物件（老式相框/旧工具/褪色的绸缎）→ 带着物件去找夏雅 → 她接过、小心擦干净。

核心台词方向（文风须过审查）：

- 夏雅："这个啊……以前大家搬家的时候，都舍不得丢。"
- 夏雅："镇上有的人走了，东西留下来了。总得有人记得它们。"

验收：

- 触发自然（依赖 P1-1 的旧物件事件，不强行打断）
- 夏雅形象 = 用行动表达（擦干净物件），不宣言
- 复用一次性事件模式，读档不重复触发

## P2 世界复苏

### P2-1 FarmRestore 扩展：marketSquare

目标：新增第四个恢复点 `marketSquare`（集市广场），让玩家第一次用行动修复一个公共区域。

> ⚠️ **命名纪律（硬性）**：`FarmRestore` 当前已承担**区域复兴状态管理**职责（garden / oldHouse / forestRoad / marketSquare），历史名字已不准确，但**暂不改名**，避免影响已有引用（`FarmRestore.ts` / `isRestored` / `getRevivalLevel` / SaveSystem 的 `worldRestore` 序列化）。任何 Agent 不得以"名字不合理"为由重构改名——改名需制作人单独批准。

文件：

- `src/data/FarmRestore.ts`（`RESTORE_KEYS` 新增 `'marketSquare'`，`RESTORE_PROJECTS` 新增配置，复用 `getProjectShortfall` / `getQuickBuyCost`）
- `src/scenes/MapScene.ts`（交互物 + 环境变化演出）
- `public/assets/maps/town.json`（集市区域两态：荒废/修复；依赖 P1.5 若确认扩容）
- `src/systems/EventManager.ts`（一次性触发）

> **依赖**：若 P1.5 Town 扩容未确认，marketSquare 仍可在现有 town 地图内的预留空地施工（空间容器待定，不阻塞本任务）。

状态变化：

- **before**：荒废（摊位破败、无灯光、无人）
- **after**：摊位 / 灯光 / NPC（集市重新有人）

三个反馈（缺一不可）：

1. **地图**：区域视觉变化（荒废 → 修复）
2. **人物**：NPC 行为/站位变化
3. **对白**：NPC 台词变化（见 P2-2）

验收：

- 修复完成后环境变化**持久化**（`worldRestore.marketSquare = true`，SaveSystem 向后兼容）
- 复兴度派生 `getRevivalLevel()` 兼容（`marketSquare` 计入后，Lv2 条件仍正确）

## 三 Agent 分工

> **文件边界（硬性）**：`src/systems/StorySystem.ts` 同一时间**只允许一个 Agent 写入**。分工如下，Agent A 与 Agent C 分别负责 StorySystem 的"状态流转"与"对话数据"，**不共享同一文件**。

| Agent | 职责 | 负责内容 | 禁止 |
|---|---|---|---|
| **Agent A 系统** | Chapter / Save / Event / Story **状态流转** | `ChapterSystem`、`SaveSystem`、`EventManager`、`StorySystem.ts` **状态机**（`getStoryStep`/`setStoryStep`/触发判定/`advanceStory`） | ❌ 改地图；❌ 改对话文案（文案属 C） |
| **Agent B 场景** | town / house / FarmRestore / 视觉变化 | `public/assets/maps/town.json`、`MapScene.ts` 场景层、`FarmRestore` 扩展、环境两态演出 | ❌ 改剧情状态（对白/事件 key 不得自行增删） |
| **Agent C 内容** | 对白数据 / NPC 文本 / MemoryFlashback | **`StorySystem.ts` 对话常量**（`*_DIALOGUE`）、`NPCSystem.ts` 台词分支、`MemoryFlashbacks.ts` 记忆数据、`DialogueData` | ❌ 新增系统；❌ 改存档结构；❌ 改状态机逻辑 |

协作边界：

- 事件 key（`ch1_*`）与状态机由 Agent A 定义为准，B/C 引用
- 对话数据文件与状态机文件**分人分文件**，禁止 A/C 并发写 `StorySystem.ts`
- 三 Agent 严禁同时操作 `main`（见 AGENTS.md Git 协作规则，提交统一由 opencode/制作人执行）

## 四 开发纪律

每个任务提交前**必须**依次通过：

```
tsc
→ build
→ 相关 probe（tests/probes/ 相关探针）
→ 人工体验（移动端只支持横屏验收）
```

禁止：

- ❌ 新造平行系统（已有 `FarmRestore` / `EventManager` / `NPCSystem` 则复用）
- ❌ 为小需求修改核心架构
- ❌ 增加未确定玩法
- ❌ **MiniGame（捕虫/钓鱼/QTE 等）不进第一章**——第一章目标不是小游戏，而是让玩家产生"我想继续看看这个镇子以后会变成什么样"。小游戏方向保留至后续章节讨论，禁止本次排期插入。
- ❌ **"顺便优化架构"**：第一章最危险的不是代码量，而是 AI 看到新章节后开始"顺便重构任务系统 / 顺便升级 NPC 框架 / 顺便做通用事件编辑器 / 顺便改 FarmRestore 名字"——这些是项目延期杀手。

**当前路线：垂直切片 > 系统完善。**
